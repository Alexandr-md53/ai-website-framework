## Что за проект

**VideoShop** — универсальный шаблон интернет-магазина.
- Владелец магазина управляет каталогом через веб-панель
- Не требует редактирования кода / JSON / БД
- VideoShop — первый демонстрационный магазин

## Ключевые решения (архитектурные, из ранних этапов)

- **D1** slug только в `slug_registry`; **D2** `update_record_cas`; **D3** `entity_id INTEGER`;
  **D5** hard delete + release slug в одной транзакции; **D6** resolver current/redirect/not_found;
  **D7** явный `entity_type`; **D9** released хранятся бессрочно; **D10** без tenant/language в slug.
- **S6:** `journal_mode=DELETE`, `synchronous=FULL`, WAL не включать; `busy_timeout=5000`;
  retry только по `SQLITE_BUSY`; `foreign_keys=ON`; разделение read/write scopes.
- **S7:** явный путь к БД; `backup()` — основной механизм; restore только с подтверждением
  и pre-restore snapshot.

## Known limitations S5 — publications (2026-10-28)

Статус: **KNOWN LIMITATION**. Публикационная подсистема реализована в S1–S5.4
(схема v9). Раздел фиксирует принятые ограничения; исправления в S5.5 не выполнялись.
Каждое ограничение подтверждено аудитами и тестами.

### GAP-1 — Публикации без jobs не видны в списке (S5.3, A12.1)

- **Наблюдаемое:** список `/admin/publications` строится из `list_jobs()`; публикация
  с нулём jobs (сбой второго шага после `create_publication`) в списке не отображается.
- **Риск:** оператор видит сообщение «publication created (id=N), jobs NOT scheduled»,
  но не находит публикацию в списке.
- **Обход:** в сообщении есть `publication_id`; при необходимости открыть
  `/admin/publications/{id}/jobs` (S5.4) — при появлении jobs страница покажет их.
- **Устранение:** core-метод `list_publications` — отдельное решение владельца;
  в S5.5 не реализуется.
- **Решение владельца:** требуется (приоритет низкий/средний).

### GAP-2 — Поиск job через list_jobs(publication_id, limit=1000) (S5.4)

- **Наблюдаемое:** `POST /admin/jobs/{job_id}/retry-as-new` находит job перебором
  `list_jobs(publication_id=…, limit=1000)`; при >1000 jobs у публикации возможен
  ложный 404.
- **Риск:** retry из UI недоступен при большом числе jobs одной публикации.
- **Обход:** увеличить limit (в пределах API) либо использовать альтернативный путь
  разрешения задачи; прямой фильтр по `job_id` требует core-метода.
- **Устранение:** core-метод `get_job(job_id)` — отдельное решение владельца.
- **Решение владельца:** требуется.

### GAP-3 — Повторный retry_as_new создаёт дополнительный job (S5.4)

- **Наблюдаемое:** каждое успешное нажатие retry-as-new создаёт новый job
  (новый `scheduled_for` → новый `idempotency_key`). PRG и предупреждение UI
  не дают серверной идемпотентности операторского действия.
- **Риск:** при двойном клике/повторном подтверждении появляются несколько job
  на одну публикацию/канал/язык.
- **Обход:** UI показывает предупреждение и работает по PRG; оператор проверяет
  список jobs перед повторным действием.
- **Устранение:** серверная идемпотентность операторского действия (operator-action-key
  либо проверка «уже есть queued job для канала/языка») — core-изменение.
- **Решение владельца:** требуется (приоритет средний).

### GAP-4 — Actor-аудит отсутствует в publication_events (S5.4)

- **Наблюдаемое:** `publication_events` содержит `at`, `level`, `message`; поля
  «кто выполнил действие» (admin username) нет.
- **Риск:** при разборе инцидентов нельзя доказательно установить автора
  `resolve_uncertain` / `retry_as_new`; фиксируется только факт.
- **Обход:** контекст запроса (admin username) доступен только в момент действия;
  в БД аудита нет.
- **Устранение:** поле `actor` в `publication_events` (миграция v10) или отдельная
  таблица admin-events — schema/core-изменение.
- **Решение владельца:** требуется.
